# Bilingual interface coverage

Implementation uses request-local locale context, source-level translations, and separately fetched Chinese/English catalogs. It does not replace DOM text or translate user-authored form values.

## Static evidence

- Scanned src; inventory records 330 page/component files and 3460 literal translation references.
- English catalog: 3552 entries; source catalog: 2741 keys/aliases.
- Missing fixed JSX or catalog entries: 0.
- Public API messages: 691 occurrences / 607 unique literals or templates; 0 missing translations.

## Verification

- Native validation tests: 5 passed (locale switching, edited input preserved, business custom validity precedence, handler cleanup, form reset and detached-field pruning).
- npm run typecheck: passed after UI changes.
- node --test test/i18n.test.cjs: 10 passed; includes exact catalog resolution, interpolation, request-local locale isolation, source error translation, safe plain text, and switching language without clearing an edited input.
- Related homepage/admin palette/festival runtime tests: 21 passed.
- Related comments/admin article-list tests: 12 passed. Baseline test updates retain all style/permission/behavior assertions; comment text-node segmentation differs while visible text is retained.
- Actual route verification is recorded by the integration audit in .cache/bilingual-route-qa/results.json and focused-results.json, with viewport screenshots. Consult the final integration report for the exact final run counts.

## Deliberate boundaries and remaining verification

- Source scanning detects literal translated calls and direct Chinese JSX/attributes. It cannot prove correctness of arbitrary computed data flows, authored content, or native third-party UI.
- API scanning covers public message/error object fields and known fail helpers. Computed aliases, concatenation, internal exceptions and database/user-provided text require flow review.
- API-derived fixed errors are translated at render boundaries. Unknown errors are not sent to a translation service; generic missing-message fallback is not evidence of full coverage.
- Native invalid events use shared selected-language messages (required/type/pattern/length/range/step). Input/change clears only errors owned by this handler; business custom errors are preserved. The browser retains its native validation if the optional handler chunk cannot load offline. Native date-picker controls and browser chrome remain browser-controlled.
- Real device touch behavior, screen-reader pronunciation and all combinations of enabled integrations require manual acceptance. No production actions were performed.
